# Kvitto Payments API

Сервис приёма оплаты курса онлайн-школы через Квитто: тарифы, создание платежа (карта, СБП, рассрочка),
промокод, идемпотентность по `Idempotency-Key` и вебхук банка со сменой статусов.

**Стек:** Python 3.11+, FastAPI, Pydantic v2, SQLAlchemy 2, SQLite, pytest + httpx, ruff.

## Запуск

Нужен Python 3.11 или новее.

```bash
git clone <repo-url> kvitto-payments && cd kvitto-payments
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
cp .env.example .env               # Windows: copy .env.example .env
alembic upgrade head               # создаёт схему БД миграциями
uvicorn app.main:app --reload
```

- API: http://127.0.0.1:8000, Swagger UI: http://127.0.0.1:8000/docs
- Схему БД создают миграции Alembic (`alembic upgrade head`), тарифы добавляются при старте
  приложения. Без миграций приложение не стартует и подсказывает, какую команду выполнить.
- Настройки — переменные окружения или `.env`: `DATABASE_URL` и `WEBHOOK_SECRET` (секрет подписи
  вебхуков). Без `WEBHOOK_SECRET` сервис работает, но все вебхуки отклоняются с 401.

## Тесты и линтер

```bash
pytest
ruff check .
ruff format --check .
```

Каждый тест получает свою копию SQLite-базы, созданной миграциями (миграции применяются один раз
за прогон), и отдельный тест сверяет миграции с моделями. Тесты проверяют не только код ответа, но и
результат: суммы и график против значений из задания, количество платежей в БД, неизменность
платежа после 409 и 404.

## Эндпоинты

| Запрос | Ответ |
|---|---|
| `GET /tariffs` | 200 — `[{id, title, price}]` |
| `POST /payments` | 201 — платёж создан; 200 — повтор с тем же `Idempotency-Key`; 409 `{"error": "idempotency_key_reused"}` — ключ уже использован с другим телом; 422 — ошибка валидации |
| `GET /payments?email=&status=&limit=&offset=` | 200 — список платежей, новые сначала; 422 — неверный фильтр |
| `GET /payments/{id}` | 200 — платёж; 404 `{"error": "payment_not_found"}` |
| `POST /webhooks/bank` | 200 `{"result": "ok"}`; 401 `{"error": "invalid_signature"}`; 404 `{"error": "payment_not_found"}`; 409 `{"error": "invalid_transition"}` |

Все суммы — целые копейки: `19 900 ₽ → 1990000`.

## Примеры запросов

На Windows используйте Git Bash или `curl.exe` (в PowerShell `curl` — это другая команда).

Список тарифов:

```bash
curl http://127.0.0.1:8000/tariffs
```
```json
[{"id":1,"title":"basic","price":990000},{"id":2,"title":"standard","price":1990000},{"id":3,"title":"premium","price":2990000}]
```

Оплата картой с промокодом (регистр промокода и email не важен):

```bash
curl -X POST http://127.0.0.1:8000/payments \
  -H "Content-Type: application/json" \
  -d '{"tariff_id": 2, "email": "Student@Example.com", "method": "card", "promo_code": "kvitto10"}'
```
```json
{"id":"220dda84-...","status":"pending","tariff_id":2,"amount":1791000,"discount":199000,"method":"card","installment_months":null,"schedule":null,"email":"student@example.com","created_at":"2026-10-11T08:47:57.830268Z"}
```

Рассрочка на 3 месяца с ключом идемпотентности. Повтор этого же запроса вернёт тот же платёж
с кодом 200; тот же ключ с другим телом — 409 `{"error": "idempotency_key_reused"}`:

```bash
curl -X POST http://127.0.0.1:8000/payments \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-1001" \
  -d '{"tariff_id": 2, "email": "student@example.com", "method": "installment", "installment_months": 3}'
```
```json
{"id":"f51c3b3f-4c17-44e3-ac63-c06c425ea3d0","status":"pending","tariff_id":2,"amount":1990000,"discount":0,"method":"installment","installment_months":3,"schedule":[663334,663333,663333],"email":"student@example.com","created_at":"2026-10-11T08:47:57.849716Z"}
```

Получить платёж (подставьте свой `id`); несуществующий — 404 `{"error": "payment_not_found"}`:

```bash
curl http://127.0.0.1:8000/payments/f51c3b3f-4c17-44e3-ac63-c06c425ea3d0
```

Список платежей с фильтрами (все параметры необязательны; `limit` — 1…100, по умолчанию 50):

```bash
curl "http://127.0.0.1:8000/payments?email=Student@Example.com&status=pending&limit=10&offset=0"
```

Вебхук банка. Заголовок `X-Signature` — HMAC-SHA256 от тела запроса с секретом `WEBHOOK_SECRET`
в hex; подписываются ровно те байты, что уходят в `-d`. `pending → succeeded` — 200
`{"result":"ok"}`; повторно отправить `failed` — 409 `{"error":"invalid_transition"}`, статус не
изменится; без подписи или с неверной — 401 `{"error":"invalid_signature"}`:

```bash
BODY='{"payment_id": "f51c3b3f-4c17-44e3-ac63-c06c425ea3d0", "status": "succeeded"}'
SIGNATURE=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "dev-webhook-secret" | sed 's/^.* //')
curl -X POST http://127.0.0.1:8000/webhooks/bank \
  -H "Content-Type: application/json" \
  -H "X-Signature: $SIGNATURE" \
  -d "$BODY"
```

## Решения и допущения

**Деньги.** Только `int` в копейках — в БД, в API и в расчётах; `float` и `round()` не используются.
Сумму считает сервер по цене тарифа из БД, клиент передать её не может (лишние поля → 422).
Скидка — `(price * percent + 50) // 100`, то есть округление половины копейки вверх. Инвариант:
`amount + discount == price`. Для текущих тарифов 10% делится нацело, но формула верна для любой цены.

**Рассрочка.** `divmod(amount, months)`: остаток в копейках раскладывается по одной на первые платежи,
поэтому сумма графика всегда ровно равна `amount`: `1990000 / 3 → [663334, 663333, 663333]`.
График сохраняется в БД при создании платежа и не пересчитывается задним числом.

**Промокод.** `KVITTO10` без учёта регистра и пробелов по краям; пустая строка — как отсутствие
промокода. Принимаются только ASCII-символы: иначе `"kvıtto10"` (турецкая `ı`) после `upper()`
совпал бы с кодом. Неизвестный код — 422 в стандартном формате FastAPI.

**Валидация.** Числа строгие: `"2"`, `2.0` и `true` вместо целого — 422. `tariff_id` ограничен сверху
максимумом `INTEGER` в PostgreSQL (2 147 483 647), иначе огромное число роняло бы запрос с 500.
`installment_months` (3, 6, 12) обязателен для рассрочки и запрещён для `card`/`sbp`.
Несуществующий тариф — 422 (это ошибка в теле запроса), в том же стандартном формате.

**Email.** Хранится целиком в нижнем регистре: `Student@Example.com` и `student@example.com` —
один получатель. Адрес с именем (`"Иван <ivan@example.com>"`) отклоняется (422), а не переписывается
молча.

**id платежа и 404.** `id` — UUID, чтобы платежи нельзя было перебирать. На любой несуществующий
`id` — в том числе не-UUID вроде `999999` в пути или в вебхуке — ответ 404, а не 422: клиент не
обязан знать формат наших идентификаторов, для него это просто «платежа нет».

**Формат ошибок.** 422 — стандартный ответ FastAPI `{"detail": [...]}`, как требует задание: это
ошибка формата запроса с указанием поля. Бизнес-ошибки — запрос корректен, но выполнить его нельзя —
отдаются одинаково: `{"error": "<код>"}` (`payment_not_found`, `invalid_transition`,
`idempotency_key_reused`). Клиенту достаточно смотреть на машиночитаемый код.

**Идемпотентность.** На `idempotency_key` стоит UNIQUE-индекс, а вместе с платежом хранится SHA-256
провалидированного тела запроса. Повтор с тем же телом — 200 и тот же платёж (в текущем статусе).
При гонке двух одинаковых запросов второй получает `IntegrityError` от БД, делает rollback и
возвращает платёж, созданный первым. Проверка «сначала SELECT» сама по себе от дублей не защищает.

**Осознанное отступление от задания: тот же ключ с другим телом — 409.** Задание говорит «вернуть
его же с кодом 200», но вернуть старый платёж на запрос с другим тарифом опасно: клиент решит, что
оплатил premium, а в БД basic. Поэтому ошибка, а не чужой платёж. 422 у нас означает ошибку формата
запроса, поэтому выбран 409 Conflict. Хэш считается от нормализованных данных, поэтому промокод или
email в другом регистре — это тот же запрос, а не конфликт.

**Статусы.** Разрешены только `pending → succeeded`, `pending → failed`, `succeeded → refunded`.
Смена статуса — один атомарный `UPDATE ... WHERE id = :id AND status IN (:allowed)`: если
одновременно придут `succeeded` и `failed`, применится ровно один, второй получит 409.
Повтор того же статуса (`succeeded → succeeded`) — тоже 409, как требует задание.

**Список платежей.** Фильтр по `email` — точное совпадение после той же нормализации, что при
создании (нижний регистр), поэтому `Student@Example.com` найдёт `student@example.com`. `status` —
одно из значений enum, иначе 422. Сортировка — новые сначала, при равном `created_at` — по `id`,
чтобы страницы не перемешивались. `offset` ограничен сверху, как и `tariff_id`: огромное значение
дало бы 500 из БД. На `email` и `status` есть индексы.

**Подпись вебхука.** `X-Signature` = HMAC-SHA256 от сырых байтов тела с `WEBHOOK_SECRET`, в hex
(регистр не важен). Сравнение — `hmac.compare_digest`: время не зависит от того, где расхождение,
поэтому подпись нельзя подбирать посимвольно по времени ответа. Подпись проверяется до валидации
тела: неподписанный запрос получает 401, а не подсказку 422 о неверных полях. Значения секрета по
умолчанию в коде нет — известный всем секрет хуже отсутствующего; если он не задан, все вебхуки
отклоняются (fail closed), а при старте пишется предупреждение.

**Миграции.** Схему создаёт только Alembic, `create_all` в приложении нет — иначе схема
расходилась бы. Миграции — отдельный шаг перед запуском, а не код в старте приложения: несколько
воркеров запускали бы их одновременно. Адрес БД миграции берут из того же `DATABASE_URL`, что и
приложение. Тесты идут на схеме из миграций, а `test_migrations_match_models` падает, если модель
изменили без миграции. Новая миграция: `alembic revision --autogenerate -m "..."` — и обязательно
прочитать результат: в первой миграции автогенерация вставила тип приложения без импорта и
задублировала CHECK-ограничения enum.

**Время.** `created_at` хранится и отдаётся в UTC с часовым поясом.

## Что бы доработал в продакшене

- Повторный вебхук с тем же статусом отвечать 200 без изменений: банки повторяют доставку.
- Срок жизни `Idempotency-Key` (например, 24 часа) и привязка ключа к магазину.
- Авторизация для `GET /payments`: список отдаёт email всех плательщиков, по заданию авторизация не
  нужна, но в продакшене это эндпоинт только для админки. Плюс keyset-пагинация вместо `offset`:
  при новых платежах между запросами страницы с `offset` сдвигаются.
- Журнал изменений статусов (кто, когда, из какого в какой) для разбора спорных платежей.
- Метка времени в подписи вебхука: сейчас перехваченный подписанный запрос можно отправить повторно.
  Вреда от этого немного — повтор того же перехода получит 409, — но защита от replay нужна.

## Структура

```
app/
  main.py              фабрика приложения, lifespan: создание таблиц и тарифов
  config.py            настройки из окружения / .env
  signatures.py        HMAC-подпись вебхуков
  db.py                engine, сессия на запрос, тип UTCDateTime
  models.py            Tariff, Payment
  schemas.py           Pydantic-схемы запросов и ответов, валидация
  enums.py             статусы, способы оплаты, таблица переходов
  money.py             расчёт скидки и графика рассрочки (чистые функции)
  errors.py            ответ {"error": "..."} для бизнес-ошибок
  seed.py              тарифы по умолчанию
  routers/             HTTP-слой: tariffs, payments, webhooks
  services/            бизнес-логика: создание и поиск платежа, смена статуса
migrations/            миграции Alembic (alembic.ini — в корне)
tests/                 pytest: деньги, платежи, идемпотентность, вебхуки, миграции
```

Работа с ИИ описана в [AI_LOG.md](AI_LOG.md), правила для ассистента — в [CLAUDE.md](CLAUDE.md).
